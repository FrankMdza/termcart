# Nintendo 64 in termcart

## Verdict

Moderately hard, and most of the work is outside rendering. The ParaLLEl N64 core builds on this M2 with only the software renderer, Angrylion, and the aarch64 dynarec. Built that way it never asks for an OpenGL or Vulkan context and hands XRGB8888 frames to `retro_video_refresh`, the same path mGBA uses. I loaded it from a throwaway ctypes harness with public domain test ROMs and got correct frames: text from the CPU test, shaded 3D cubes from an RDP triangle test.

What it costs:

- **Host work.** No GPU code. We need a handful of new environment calls, frame aspect handling, analog input, and runtime sample rate changes. I'd guess two to four days of focused work in `src/`.
- **CPU.** Test ROMs use 0.2 to 0.7 of a core at 60 fps. Real 3D games will need a lot more, because Angrylion rasterizes every pixel exactly like the hardware. My estimate is 1.5 to 4 M2 cores for typical games, with some titles below full speed. That number is a guess until we run a real game.
- **Bandwidth.** Angrylion always outputs 640 pixels wide: 640x240 for most games, 640x480 for interlaced ones. Over `t=s` shared memory that costs nothing on the pty. Over `t=d` it is 37 MB/s of base64 at 640x240 and 74 MB/s at 640x480, which is too much. N64 needs the shm transport.
- **Input.** Playable on a keyboard, but clumsy. The stick becomes 8-way digital at a fixed deflection, and the C buttons need four more keys.

What we would ship first: ParaLLEl N64 with Angrylion, the HLE RSP, the aarch64 dynarec, 4 renderer threads, the shm transport, the core's independent C-button layout, and a keyboard stick with a walk modifier. No hardware render support. I would not start with GLideN64 or ParaLLEl-RDP. They need an offscreen GL or Vulkan context plus a readback every frame, and on macOS that means deprecated OpenGL 4.1 or MoltenVK. Add one of them only if real games turn out too slow with Angrylion.

### ParaLLEl N64

The GitHub repo is now the "Parallel Launcher Edition" fork, with GLideN64 added and a lot of recent work on macOS ARM and on running Angrylion with the HLE RSP. I read commit [`6f23339`](https://github.com/libretro/parallel-n64/tree/6f233392445dcef4188a321d4ba65a776f0e1672).

Rendering:

- [`Makefile` L303-L346](https://github.com/libretro/parallel-n64/blob/6f233392445dcef4188a321d4ba65a776f0e1672/Makefile#L303-L346). On native Apple Silicon the osx block sets `WITH_DYNAREC = aarch64` and `-mmacosx-version-min=11.0`. `HAVE_OPENGL`, `HAVE_PARALLEL` and `HAVE_THR_AL` are plain make variables. With `HAVE_OPENGL=0`, [lines 887-892](https://github.com/libretro/parallel-n64/blob/6f233392445dcef4188a321d4ba65a776f0e1672/Makefile#L887-L892) drop GLideN64, Glide64, gln64 and Rice.
- [`libretro/libretro.c` L393-L421](https://github.com/libretro/parallel-n64/blob/6f233392445dcef4188a321d4ba65a776f0e1672/libretro/libretro.c#L393-L421). On `auto` the core picks ParaLLEl-RDP if Vulkan came up, Glide64 if GL did, and Angrylion otherwise.
- [`retro_load_game` L3082-L3112](https://github.com/libretro/parallel-n64/blob/6f233392445dcef4188a321d4ba65a776f0e1672/libretro/libretro.c#L3082-L3112). When the plugin is Angrylion, the core skips both `retro_init_vulkan` and `retro_init_gl`, so `RETRO_ENVIRONMENT_SET_HW_RENDER` is never called. My harness confirmed this: it logged every environment call and `SET_HW_RENDER` never showed up.
- [`present_frame` L954-L1004](https://github.com/libretro/parallel-n64/blob/6f233392445dcef4188a321d4ba65a776f0e1672/libretro/libretro.c#L954-L1004). Angrylion calls `video_cb(pixels, w, h, pitch)` with real pixels. ParaLLEl-RDP and the GL plugins pass `RETRO_HW_FRAME_BUFFER_VALID` instead.
- [`retro_init_vulkan` L1405](https://github.com/libretro/parallel-n64/blob/6f233392445dcef4188a321d4ba65a776f0e1672/libretro/libretro.c#L1405) asks for `RETRO_HW_CONTEXT_VULKAN` and a context negotiation interface. That is only reached when the plugin is ParaLLEl-RDP.
- `retro_init` asks for `RETRO_PIXEL_FORMAT_XRGB8888`. The host already converts that.

RSP:

- [`core_settings_autoselect_rsp_plugin` L510](https://github.com/libretro/parallel-n64/blob/6f233392445dcef4188a321d4ba65a776f0e1672/libretro/libretro.c#L510) defaults to the HLE RSP, and the comment at [L496](https://github.com/libretro/parallel-n64/blob/6f233392445dcef4188a321d4ba65a776f0e1672/libretro/libretro.c#L496) says Angrylion can now rasterize the HLE display list. This matters for cost, because the alternative LLE RSP is the cxd4 interpreter. The fork's `rdp_emit_*.c` files in `mupen64plus-video-angrylion/` implement it. Homebrew with an unknown IPL3, such as libdragon games, gets routed to LLE.
- ParaLLEl-RSP, the RSP JIT, is hardwired to `PARALLEL_RSP_ARCH := x86_64` in [`Makefile.common` L659-L660](https://github.com/libretro/parallel-n64/blob/6f233392445dcef4188a321d4ba65a776f0e1672/Makefile.common#L659-L660), so we build without it.

Renderer options in the build I made:

- `parallel-n64-gfxplugin`: only `angrylion`. The default is `angrylion` when GL is compiled out, see [`libretro_core_options.h` L962-L966](https://github.com/libretro/parallel-n64/blob/6f233392445dcef4188a321d4ba65a776f0e1672/libretro/libretro_core_options.h#L962-L966).
- `parallel-n64-rspplugin`: `auto`, `hle`, `cxd4`.
- `parallel-n64-cpucore`: `pure_interpreter`, `cached_interpreter`, `dynamic_recompiler`. The last one is Ari64's new_dynarec.
- `parallel-n64-angrylion-multithread`: `off`, `all threads`, `1` to `8`. "All threads" stops at 8, see `PARALLEL_AUTO_MAX_WORKERS` in `parallel_al.c`, which on an M2 includes the 4 efficiency cores.
- `parallel-n64-angrylion-vioverlay`: `Filtered`, `AA+Blur`, `AA+Dedither`, `AA only`, `Unfiltered`, `Depth`, `Coverage`.
- `parallel-n64-angrylion-sync`, `-overscan`, `-deinterlace`, plus `parallel-n64-upscaling` at 1x, 2x, 4x or 8x. Leave upscaling at 1x for a terminal.

### Mupen64Plus-Next

I read commit [`12edd2c`](https://github.com/libretro/mupen64plus-libretro-nx/tree/12edd2c74a517ff86dfa8cfc71ad75e4c10486d5) and did not build it, for these reasons:

- [`Makefile` L399-L428](https://github.com/libretro/mupen64plus-libretro-nx/blob/12edd2c74a517ff86dfa8cfc71ad75e4c10486d5/Makefile#L399-L428), the osx block, sets `WITH_DYNAREC =` and `-DNO_ASM` and links `-framework OpenGL`. On macOS the R4300 runs on the cached interpreter at best. Its new_dynarec has no `MAP_JIT` or `pthread_jit_write_protect_np` code at all.
- [`Makefile.common`](https://github.com/libretro/mupen64plus-libretro-nx/blob/12edd2c74a517ff86dfa8cfc71ad75e4c10486d5/Makefile.common) always compiles GLideN64. There is no switch to drop GL.
- [`libretro/libretro.c` L954](https://github.com/libretro/mupen64plus-libretro-nx/blob/12edd2c74a517ff86dfa8cfc71ad75e4c10486d5/libretro/libretro.c#L954). When Angrylion is selected, the core overrides an HLE RSP request and forces ParaLLEl-RSP or cxd4. So Angrylion always pays for full RSP emulation.
- [`retro_load_game` L1970](https://github.com/libretro/mupen64plus-libretro-nx/blob/12edd2c74a517ff86dfa8cfc71ad75e4c10486d5/libretro/libretro.c#L1970) needs a GL context only for GLideN64. The default `rdp-plugin` is `gliden64`, so the host would have to set `angrylion` before load.

Its software path works the same way as ParaLLEl N64's, but it loses on CPU cost: no dynarec on macOS, and no HLE RSP with Angrylion.

## If we wanted hardware rendering

None of this is needed for the first version. It is here so the cost is on record.

**GLideN64** needs OpenGL 3.3 core, or GLES 2+. On macOS the host would:

1. Create a context with no window. `CGLChoosePixelFormat` with `kCGLPFAOpenGLProfile = kCGLOGLPVersion_GL3_Core`, `kCGLPFAAccelerated` and `kCGLPFAAllowOfflineRenderers`, then `CGLCreateContext` and `CGLSetCurrentContext`. No NSWindow is needed. macOS gives a 4.1 core context. The API is deprecated since 10.14 but still works on Apple Silicon, where Apple implements it on top of Metal.
2. Create an FBO with color and depth/stencil attachments at the core's `max_width`/`max_height`.
3. Answer `SET_HW_RENDER` by filling `get_current_framebuffer`, which returns the FBO id, and `get_proc_address`, which is `dlsym` on `/System/Library/Frameworks/OpenGL.framework/OpenGL`. Then call `context_reset` before the first `retro_run`, and `context_destroy` on unload.
4. When `video_cb` gets `RETRO_HW_FRAME_BUFFER_VALID`, read the frame back with `glReadPixels` into a PBO, map it one frame later so the read does not stall, and flip it vertically, since GL rows run bottom up.
5. Keep every core call on the thread that owns the context. GLideN64's threaded renderer option has to stay off, or we have to run its coroutine model.

The readback copies 1.2 MB per frame at 640x480 RGBA. Unified memory makes that cheap. My estimate is 0.2 to 1 ms per frame with a PBO and a few ms with a synchronous `glReadPixels`, which is fine at 60 fps. The real cost is code: roughly 300 to 500 lines of unsafe CGL and GL FFI in Rust, an `objc2`/`core-foundation` or raw `extern "C"` dependency, and a renderer that is less accurate than Angrylion. It is faster though.

**ParaLLEl-RDP** needs Vulkan. On macOS that means MoltenVK, which is not installed here (`brew list molten-vk` finds nothing), so we would ship or require the Vulkan loader plus MoltenVK. The host has to implement `retro_hw_render_interface_vulkan` and context negotiation: create the instance, device and queue, hand them to the core, accept the image the core gives through `set_image`, signal semaphores, then copy that image into a host-visible buffer and read it. That is RetroArch's Vulkan driver in miniature, a week or more of work. The fork's README says Aglab2 added MoltenVK support for ParaLLEl, so it should run, but the host side is the biggest piece of work on this list.

**Dynarec on arm64 macOS.** ParaLLEl N64 handles Apple's W^X rules in [`new_dynarec.c` L29-L56 and L9044-L9053](https://github.com/libretro/parallel-n64/blob/6f233392445dcef4188a321d4ba65a776f0e1672/mupen64plus-core/src/device/r4300/new_dynarec/new_dynarec.c#L9044-L9053). It maps the code cache with `MAP_JIT` and toggles `pthread_jit_write_protect_np` around code emission. [`arm64/assem_arm64.c` L271-L280](https://github.com/libretro/parallel-n64/blob/6f233392445dcef4188a321d4ba65a776f0e1672/mupen64plus-core/src/device/r4300/new_dynarec/arm64/assem_arm64.c#L271-L280) calls `sys_icache_invalidate` after writing. `MAP_JIT` only needs the `com.apple.security.cs.allow-jit` entitlement under the hardened runtime. Our `target/release/termcart` is ad hoc and linker signed with no runtime flag, so it needs nothing. The test bore that out: under the same kind of signing, the dynarec ran and was about 2x faster than the cached interpreter on the Mandelbrot ROM. If we ever notarize termcart with the hardened runtime, add that entitlement.

## What I built and ran

`scripts/build-n64.sh` clones ParaLLEl N64 into `.cores-src/parallel-n64`, pins it to `6f23339`, applies one patch, and runs:

```
make platform=osx HAVE_OPENGL=0 HAVE_PARALLEL=0 HAVE_PARALLEL_RSP=0 HAVE_THR_AL=1
```

Then it copies `parallel_n64_libretro.dylib` into `cores/`. The project uses plain make, not CMake, so the CMake 4 policy flag does not apply. A clean build took 17 seconds on the M2.

The patch is `scripts/patches/parallel-n64-macos-corefoundation.patch`. Without GL, `libretro.c` still includes `glsm.h`. On macOS that pulls in `CoreFoundation.h` and `MacTypes.h` after `r4300.h` has defined `hi` and `lo` as macros, and `MacTypes.h` stops compiling. The patch includes CoreFoundation first. Passing `-include` through `CFLAGS` does not work, because the dynarec's `.S` file goes through the same flags. This is worth upstreaming: nobody has built the no-GL desktop macOS variant recently.

The result is a 2.4 MB arm64 dylib that links only `libSystem` and `libc++`. No OpenGL, no Vulkan.

I tested with ROMs from [PeterLemon/N64](https://github.com/PeterLemon/N64), which is under the Unlicense. They are in `roms/test/peterlemon-n64/` with the LICENSE, and `/roms` is gitignored. The harness is `n64probe.py` in my scratchpad, outside the repo. It sets the core options, answers `SET_HW_RENDER` with false, runs N frames, logs every environment call, and dumps the last frame.

| ROM | Result | Uncapped, 1 thread | Uncapped, all threads | CPU at 60 fps |
|---|---|---|---|---|
| HelloWorldCPU32BPP320X240 | correct text | 1.5 ms/frame | 0.5 ms/frame | 0.19 to 0.24 cores |
| CubeFillTriangle16BPP320X240 | 6 shaded cubes, correct | 3.7 ms | 1.8 ms | |
| RotateRightMajorTriangle16BPP320X240 | rotating fill triangle | 6.4 ms | 2.8 ms | 0.41 cores with 1 thread, 0.68 with all |
| Mandelbrot32BPP320X240 | fractal drawn | dynarec 2.0 ms, cached interp 3.6, pure interp 4.4 | | |
| HelloWorldRDP32BPP320X240 | black frame | | | |

All runs used the dynarec, Angrylion and `rspplugin=auto`. The RDP hello world stayed black with both HLE and cxd4. I did not dig further. The other RDP tests render, so it looks specific to that ROM, but it is still open.

Every frame came back at **640x240** with pitch 2560, while `retro_get_system_av_info` reported base 640x480 and aspect 1.333. Angrylion's VI always outputs 640 wide and emits 240 lines for progressive games. Our host sizes the image from the frame's own width and height, so it would draw this at 2.67:1. See step 3 of the plan.

Environment calls the core made, beyond what the host already answers: `SET_CONTROLLER_INFO`, `SET_SUBSYSTEM_INFO`, `GET_PERF_INTERFACE`, `GET_RUMBLE_INTERFACE`, `SET_SERIALIZATION_QUIRKS`, `SET_MEMORY_MAPS`, `SET_GEOMETRY`, `GET_AUDIO_VIDEO_ENABLE` (every frame), `GET_CURRENT_SOFTWARE_FRAMEBUFFER` (every frame), and `SET_CORE_OPTIONS_UPDATE_DISPLAY_CALLBACK`. All of these work when answered false. The core reads about 80 option keys, most of them GLideN64 ones that do nothing in this build.

The test ROMs produced no audio. The audio backend ([`audio_backend_libretro.c` L22-L38 and L198](https://github.com/libretro/parallel-n64/blob/6f233392445dcef4188a321d4ba65a776f0e1672/mupen64plus-core/src/plugin/audio_libretro/audio_backend_libretro.c#L198)) skips resampling. It sends the game's real AI rate to the frontend with `SET_SYSTEM_AV_INFO` whenever the rate changes, so the host has to handle that call.

## CPU cost on the M2

What I measured:

- The fixed cost of a frame, which is emulation plus VI at 640x240 with Angrylion, is about 1.5 ms on one P-core, around 0.2 of a core at 60 fps.
- Full-screen flat triangles cost about 2 to 5 ms per frame on one thread, and threads cut that roughly in half.
- Idle renderer threads cost nothing. `parallel_al.c` parks workers on an eventcount between frames.

What I estimate, without a real game: commercial games draw textured, Z-buffered, blended triangles in 1-cycle and 2-cycle modes, often with several layers of overdraw. Angrylion runs the full RDP pipeline for every pixel, and that costs many times more than a fill. Its reputation on desktop CPUs is "full speed with several fast cores, not on one". On an M2 I would plan for:

- R4300 dynarec plus HLE RSP plus audio: 0.3 to 0.6 of a core.
- Angrylion at 320x240: 1 to 3 cores of rasterizer work, spread over 4 threads, in typical scenes.
- Host conversion and shm copy: under 0.1 of a core.

That totals 1.5 to 4 cores. Most games should reach 60 fps with 4 threads on the P-cores. The heaviest scenes may dip. Before promising anything, run three real games the user owns, such as Mario 64, Ocarina of Time and Mario Kart, through the harness, and log ms per frame for each.

## Terminal bandwidth

Bytes per frame and per second at 60 fps, for the kitty transports termcart already has:

| Frame | f=24 raw | base64 per frame | t=d at 60 fps | f=32 t=d at 60 fps |
|---|---|---|---|---|
| 320x240 | 230 KB | 307 KB | 18 MB/s | 25 MB/s |
| 640x240, what Angrylion emits | 461 KB | 614 KB | 37 MB/s | 49 MB/s |
| 640x480, interlaced games | 922 KB | 1.23 MB | 74 MB/s | 98 MB/s |

With `t=s` only the shm object name crosses the pty, under 100 bytes per frame. Ghostty still copies the pixels out of shm and uploads a texture, which at these sizes is a few hundred KB to 1.2 MB, well within its limits. `t=d,o=z` helps on flat frames, but zlib on 1 MB of 3D content each frame costs real CPU that Angrylion needs. N64 uses the default `shm` transport at f=32. Measured in Ghostty 1.3.1, f=24 saved nothing on Ghostty's side and cost us 70 to 180 µs more per frame, and halving the frame to 320 wide was not worth the lost detail.

## Analog stick and C buttons

Source: [`emulate_game_controller_via_libretro.c`](https://github.com/libretro/parallel-n64/blob/6f233392445dcef4188a321d4ba65a776f0e1672/mupen64plus-core/src/plugin/emulate_game_controller_via_libretro.c).

- **Control stick.** The core reads `RETRO_DEVICE_ANALOG`, `RETRO_DEVICE_INDEX_ANALOG_LEFT`, X and Y, as int16 from -32768 to 32767. `analog_scale` (L472) applies the `astick-deadzone` and `astick-sensitivity` options and scales to the N64 range of ±80, inverting Y. The snap-angle options can pull near-diagonals onto exact 45 degree angles.
- **C buttons, standard layout.** These come from `RETRO_DEVICE_INDEX_ANALOG_RIGHT`, either axis past a deadzone (L919-L927). The other way is to hold R2, "C Buttons Mode", which turns the face buttons into C buttons while held. On a keyboard that is awkward.
- **C buttons, alternate layout.** With `parallel-n64-alt-map = enabled`, the inputs map like this (L106-L130):

| N64 | RetroPad |
|---|---|
| A | B |
| B | Y |
| C-Right | R |
| C-Left | L |
| C-Down | A |
| C-Up | X |
| Z | L2 |
| R | R2 |
| L | Select |
| Start | Start |
| D-pad | D-pad |
| Stick | left analog |

  Every N64 button is then a digital RetroPad bit. For a keyboard host this is the layout to use, since the host only has to answer JOYPAD bits and the left stick.
- **Mouse to stick.** `parallel-n64-mouse-mode` lets `RETRO_DEVICE_MOUSE` deltas drive the stick when the stick is centered. Terminals report mouse positions in cells, not deltas, so this would be coarse. I'd skip it.

What this means for a terminal:

- The host has to answer `RETRO_DEVICE_ANALOG` in `input_state`. Today it returns 0 for anything that is not `DEVICE_JOYPAD` or not port 0.
- A keyboard stick is 8 directions at one magnitude. Holding Shift to walk could map to about 40% deflection, since many games use partial tilt for walking. A stick at full deflection on 4 keys is playable for Mario 64, though tight platforming suffers.
- Key release events matter more than on the GBA, because holding a direction is the main input. Ghostty sends releases through the kitty keyboard protocol and the host already uses them. In terminals without the protocol, the timed-release fallback will make the stick stutter.
- The N64 has 14 inputs plus the stick, so a keyboard layout needs about 18 keys. A proposal: WASD for the stick, arrows or IJKL for the C buttons, K/J or Space for A/B, Q for Z, E for R, Tab or 1 for L, Enter for Start, and the D-pad on numpad or rarely-used keys. Tab is fast forward today, so that one needs a decision.
- A real gamepad would be much better, but reading a USB/Bluetooth controller is outside what a terminal provides. It would mean adding something like `gilrs` and reading HID directly.

## Plan

1. **Ship the build.** `scripts/build-n64.sh` and the patch are in place. Upstream the CoreFoundation patch to libretro/parallel-n64.
2. **Core options per core.** For parallel-n64, the host should answer `GET_VARIABLE` with these defaults: `gfxplugin=angrylion`, `rspplugin=auto`, `cpucore=dynamic_recompiler`, `angrylion-multithread=4`, `alt-map=enabled`, `upscaling=1x`. That needs a per-core override table in the host, which the core-options code in `src/libretro/host.rs` already almost supports.
3. **Geometry.** Handle `SET_GEOMETRY` (37) and `SET_SYSTEM_AV_INFO` (32), and store `aspect_ratio`. When the image is drawn, the displayed size has to follow `aspect_ratio`, not width/height. In kitty, pass both `c=` and `r=` so Ghostty stretches 640x240 to 4:3, or resample to 320x240 in the host. The half-block renderer probably needs the same fix. Accept frame sizes that change between calls, since the size flips between 640x240 and 640x480 inside a game.
4. **Audio rate changes.** On `SET_SYSTEM_AV_INFO`, rebuild the resampler in `src/audio.rs` with the new `sample_rate` without dropping the stream. This matters for N64 because each game picks its own AI rate.
5. **Analog input.** In `input_state`, answer `DEVICE_ANALOG` (5) for `INDEX_ANALOG_LEFT` from the stick keys, ±32767 per axis, scaled by 0.4 with the walk modifier and normalized on diagonals. Answer `INDEX_ANALOG_RIGHT` as 0, since alt-map covers the C buttons. Add the N64 bindings as a second key table chosen by system. Ports 1 to 3 return 0.
6. **Small environment calls.** Return true from `SET_CONTROLLER_INFO`, `SET_SUBSYSTEM_INFO`, `SET_MEMORY_MAPS` and `SET_SERIALIZATION_QUIRKS`. Return false from `GET_RUMBLE_INTERFACE`, `GET_PERF_INTERFACE` and `GET_CURRENT_SOFTWARE_FRAMEBUFFER`. For `GET_AUDIO_VIDEO_ENABLE`, write 3, meaning video and audio, or return false. None of these block the core.
7. **Pick the transport.** Done: the default `shm` at f=32 handles 640x240 and 640x480 with no dropped frames. `direct` (49 to 98 MB/s) and `zlib` (0.7 to 1.5 ms per frame) do not keep up.
8. **Measure with real games.** Run three games the user owns through the harness, or termcart with `TERMCART_LOG`. Record ms per frame at 1, 2, 4 and 8 Angrylion threads. If typical scenes go over about 12 ms, plan the GLideN64 and CGL work from the section above. Otherwise stop here.
9. **Later, maybe.** Controller Pak and EEPROM saves go through the existing save directory and `.srm` path, so check that they persist. Add savestates through `retro_serialize` if termcart grows that feature.

No step needs `SET_HW_RENDER`. That is what makes N64 a medium-sized job instead of a large one.

## Status (2026-10-21)

Steps 2 to 7 are implemented. The host answers the parallel-n64 options (`src/libretro/options.rs`), follows `SET_GEOMETRY` and `SET_SYSTEM_AV_INFO`, reads the left stick, and draws 640-wide frames at the core's 4:3 aspect, with kitty `c=` and `r=` both set so Ghostty stretches the image. The heaviest public domain test ROM runs at 67% of one core and 30 MB in Ghostty. Step 8, measuring real games, still needs ROMs from cartridges the user owns.
